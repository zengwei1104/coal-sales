03 / HIGH

P1 高：核心业务约束或权限可被绕过

1. 修改订单数量不校验合同上限

coal-sales/.../SaleOrderServiceImpl.java:150-165

修改订单时直接保存新计划量，可将订单改为远超合同余量的数量。

建议：按“合同累计量－本单原量＋新量”重新校验，并确保新计划量不小于已发运量。

2. 销售员可以审核其他销售员的合同

coal-sales/.../ContractController.java:78-86

控制器允许 SALES 审核，与“经理审批”规则不符。

建议：审核接口仅保留经理权限，服务层同步增加角色校验。

3. 已完成、已取消订单仍能创建磅单

coal-sales/.../WeighTicketServiceImpl.java:77-97

开单时只检查订单是否存在，会产生后续无法发运的无效磅单。

建议：仅允许待发运或部分发运订单开单。

4. 存在有效磅单的订单仍能取消或删除

coal-sales/.../SaleOrderServiceImpl.java:167-200

可能留下指向已取消或已删除订单的活动磅单。

建议：取消、删除前检查未作废磅单，并结合订单行锁防止并发绕过。

5. 订单已结算数量从不更新

SaleOrder.settledQty / SettlementServiceImpl.java

结算审核后没有累加 settledQty，作废已审核结算单时也没有回退。

建议：审核时按明细汇总净重并累加；作废已审核结算单时在删除明细前回退。

6. 毛重仅校验大于皮重，缺少完整业务上限校验

coal-sales/.../WeighTicketServiceImpl.java:135-203

异常净重、超出订单或合同允许范围的发运仍可能直接扣减库存。

建议：在库存写入前校验净重范围、累计发运量及合同溢短装上限。

06 / CONCURRENCY STRATEGY

Redis 方案评估

核心结论：Redis 可以加入，但不应替代 MySQL 事务与约束。正确方向是“数据库保证最终一致性，Redis 辅助分布式协调、接口幂等与缓存”。

单后端实例：优先使用数据库事务与行锁

01开启事务
02锁定磅单并复查状态
03锁定订单并重算发运量
04原子更新库存并写流水
05提交事务后释放锁

库存更新应保留数据库余额条件，并检查影响行数，防止库存扣成负数：

UPDATE stock
SET total_qty = total_qty + ?
WHERE product_id = ?
  AND total_qty + ? >= 0;

多后端实例：Redis 作为辅助分布式锁

可使用 Redisson，按业务单据设置锁，例如 lock:weigh-ticket:{id}、lock:settlement:{id}。同时必须满足：

  • 分布式锁覆盖到数据库事务提交完成，不能在提交前提前释放。
  • 保留数据库状态校验、唯一索引和库存条件更新，不能只依赖 Redis 锁。
  • 多资源加锁采用固定顺序，避免死锁。
  • 不建议只在 Redis 中扣库存，再异步同步 MySQL，以免引入宕机、过期与一致性问题。

适合：接口幂等

通过请求唯一标识和 Redis 原子占位，配合数据库唯一约束，防止双击或网络重试造成重复开单、回款。

适合：读多写少缓存

缓存数据字典、菜单权限和部分报表数据，设置 TTL，并在写操作后及时失效。

适合：多实例协调

确实需要水平扩展时，再引入分布式锁作为数据库约束之外的协调手段。

不适合：唯一事实来源

库存、订单状态、结算状态仍应以数据库事务结果为准，不以缓存值作为最终判断依据。

07 / RECOMMENDED ROADMAP

推荐修复顺序

  1. 先修 P0：统一磅单、订单、库存、结算的事务和行锁，补充并发测试。
  2. 再修 P1：补齐合同上限、订单状态、角色权限、结算数量等核心业务校验。
  3. 随后修 P2：统一前后端字段、分页参数、状态计算和单号生成规则。
  4. 最后修 P3：处理菜单入口、按钮权限、加载状态和防重复提交。
  5. 按部署规模引入 Redis：单实例不强制；多实例时用于分布式协调、幂等和缓存。
每完成一个业务模块，应至少验证：编译通过、正常流程、非法状态拒绝、重复提交、两个并发请求，以及失败后的数据回滚。
