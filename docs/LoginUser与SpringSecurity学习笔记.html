1. LoginUser 是什么？有什么作用

LoginUser 是 Spring Security 认证体系里的「登录用户」封装类，作用是把业务实体 SysUser 包装成 Spring Security 能识别的 UserDetails 对象。

它本质上是一个「适配器 / 翻译官」

Spring Security 只认 UserDetails 接口，不认你的 SysUser。登录成功后框架需要标准格式来保存登录用户、判断密码、判断账号状态、判断权限。LoginUser 就是把 SysUser 「翻译」成 Security 的语言。

关键方法一览

方法作用
getUsername()返回登录账号，框架靠它查用户
getPassword()返回加密后的密码，框架拿它比对
getAuthorities()返回权限列表（RBAC 权限控制用）
isEnabled()判断账号是否启用（用 status == 1），为 false 则登录失败
getUserId()自定义方法：拿当前登录用户 id（高频使用）
getRoleId()自定义方法：拿角色 id（一对一）
getUser()自定义方法：拿完整 SysUser 实体

它不只是「登录凭证」

它是当前登录用户在整个后端系统里的「上下文载体」——认证、授权、审计、会话、业务取数，都靠它。

场景作用
身份认证Security 校验密码、判断账号状态
拿当前用户getUserId() 高频使用
权限控制getAuthorities() 配合 @PreAuthorize 做 RBAC
审计填充MyBatis-Plus 自动填创建人/修改人
会话管理序列化存 Redis，做 token 续期、踢人下线
业务扩展塞部门、姓名等附加信息，减少查库

2. LoginUser 替代了 SysUser 吗？

结论：不是替代，是「包装」。

对比SysUser（实体类）LoginUser（包装类）
是什么数据库表的映射登录态的封装
对应数据sys_user 表一行数据当前「登录中」的一个用户
生命周期存在数据库里，长期存在内存/Redis，随登录会话存在
用途增删改查、存数据认证、授权、拿当前登录人
谁用Service / MapperSecurity 框架、Controller

从代码看更清楚，LoginUser 内部「持有」一个 SysUser：

public class LoginUser implements UserDetails {
    private final SysUser user;   // ← 它把 SysUser 包在里面
}
打个比方 SysUser 是你这个人本身；LoginUser 是你在公司门口刷的「工牌」——工牌上有你的信息，但它不是「你」，只是代表「你」能进门的凭证。

在 Controller 层拿当前用户时，确实不再直接操作 SysUser，而是通过 LoginUser，但那只说明「读取当前登录人」这个场景用 LoginUser 更顺手，不代表 SysUser 被替代了。数据库那边，SysUser 还是唯一的主。

3. 身份认证时都用 LoginUser 吗？

基本正确。身份认证的整个流程里，核心角色就是 LoginUser。完整流程：

用户输入账号密码
      ↓
① UsernamePasswordAuthenticationFilter（拦截登录请求）
      ↓
② UserDetailsService.loadUserByUsername(username)
      ↓ 查数据库拿 SysUser，包装成 LoginUser 返回   ← 第1次出现
③ DaoAuthenticationProvider 校验
      ↓ 拿 LoginUser.getPassword() 比对密码
      ↓ 检查 isEnabled() 等账号状态
④ 认证成功 → 生成 Authentication 对象
      ↓ principal 存的就是这个 LoginUser          ← 第2次出现
⑤ 存入 SecurityContext（整个请求期间都能拿到）
      ↓
⑥ Controller / Service 里取出 LoginUser 用        ← 第3次出现
前后端分离 + JWT 的特殊点 你的项目用 JWT，所以不是「登录时存起来一直用」，而是：登录 → 生成 JWT（只存 userId）→ 后续请求带 JWT → 自定义 Filter 解析 JWT 拿到 userId → 再查一次库，重新构造 LoginUser 塞进 SecurityContext。即每个请求都重新构造一次。

4. LoginUser 在项目中的 6 处实际用法

① 认证入口 —— 包装 SysUser

UserDetailsServiceImpl.loadUserByUsername()：按用户名查库，包装成 LoginUser（权限传空 list）。

return new LoginUser(user, Collections.emptyList());

② 登录签发 token —— 拿到完整用户

AuthService.login()：认证成功后从 principal 取 LoginUser，再 getUser() 拿 SysUser 组装返回信息。

LoginUser loginUser = (LoginUser) authentication.getPrincipal();
SysUser user = loginUser.getUser();

③ JWT 过滤器 —— 每个请求重建 LoginUser

JwtAuthenticationFilter.doFilterInternal()：用 token 里的 userId 回查库，重新构造 LoginUser 塞进上下文，同时校验 status==1 实现「禁用用户立即失效」。

SysUser user = sysUserMapper.selectById(userId);
LoginUser loginUser = new LoginUser(user, Collections.emptyList());
UsernamePasswordAuthenticationToken authentication =
    new UsernamePasswordAuthenticationToken(loginUser, null, loginUser.getAuthorities());
SecurityContextHolder.getContext().setAuthentication(authentication);

④ Controller 层 —— @AuthenticationPrincipal 自动注入

UserController 用 Spring Security 官方注解 @AuthenticationPrincipal 直接注入 LoginUser，配合 checkAdmin() 做管理员校验。

public Result<Void> updatePassword(...,
        @AuthenticationPrincipal LoginUser loginUser) { ... }

⑤ 业务层 —— 数据归属校验

SaleOrderServiceImpl.checkOwner()：用 getRoleId() 判断角色 + getUserId() 判断「是不是自己创建的订单」，实现数据级权限（销售员只能操作自己的订单）。

⑥ 两个横切点

  • MyMetaObjectHandler —— MyBatis-Plus 自动填充 createBy，从 getUserId() 取当前登录人。
  • LogAspect —— 操作日志切面，用 getUserId() + getUsername() 记录操作人。
小结 你的 LoginUser 已贯穿完整链路：认证 → 签发 token → 请求鉴权 → 接口注入 → 角色/数据权限 → 审计。这是当前主流的 JWT + Spring Security 标准写法，不需要改。

5. 为什么要用 LoginUser（为什么不能直接塞 SysUser）

根本原因：类型不匹配

Spring Security 内部只操作 UserDetails 接口。你的 SysUser 是普通实体类，没实现那些方法，Security 拿到它根本不知道「密码是哪个字段、账号算不算启用」。所以必须有类去实现 UserDetails，把 SysUser 的字段「翻译」成接口要求的方法。

为什么不直接让 SysUser 实现 UserDetails？

问题说明
职责混乱实体类是纯数据模型，混入安全协议违反单一职责
耦合实体类被迫依赖 security 包，换框架难
序列化隐患带 Collection<GrantedAuthority>，缓存/序列化到 Redis 易出问题
扩展困难业务方法（getUserId/getRoleId/getUser）硬塞进实体会臃肿

「包装」比「改造」更干净。

准确结论

Spring Security 不强制「额外写包装类」，只要求「必须有一个 UserDetails 的实现类」。三种做法：

  1. 自定义包装类（你用的 LoginUser）✅ 推荐 —— 实体干净、可加业务方法
  2. 用 Security 自带的 User —— 零代码，但拿不到 SysUser 自定义字段
  3. 让实体类直接实现 UserDetails —— 能用，但不推荐（耦合）

6. Spring Security 的职责与组成

两大核心职责

职责英文解决的问题
认证Authentication你是谁？—— 校验账号密码
授权Authorization你能干什么？—— 判断有无权限

附加能力：防 CSRF、防会话固定、密码加密（BCrypt）、记住我、CORS 等。

认证流程关键组件

组件作用你项目的对应
SecurityFilterChain过滤器链，请求先经过一串 FilterSecurityConfig 里的规则
AuthenticationManager认证总调度，把活派给 ProviderAuthService 里注入并调用
AuthenticationProvider真正执行认证（如 DaoAuthenticationProvider）框架默认
UserDetailsService按用户名查库返回 LoginUserUserDetailsServiceImpl
PasswordEncoder密码加密/比对（BCrypt）SecurityConfig 里的 BCryptPasswordEncoder
SecurityContextHolder存当前登录用户AuthUtil / MetaObjectHandler / LogAspect

授权流程关键组件

组件作用
AccessDecisionManager访问决策（投票机制）
@PreAuthorize 等注解方法级鉴权
GrantedAuthority权限标识对象（SimpleGrantedAuthority）

你项目里已经跑通这套体系，但权限校验目前是靠 checkAdmin / checkOwner 手动判断 roleId（粗粒度），还没用 @PreAuthorize（细粒度）。

7. getAuthorities() 方法与泛型拆解

方法签名逐段拆解

public Collection<? extends GrantedAuthority> getAuthorities()
部分含义
public公开方法（接口方法必须 public）
Collection<...>返回一个集合（List/Set），一个用户有多个权限
GrantedAuthority权限接口，核心方法 getAuthority() 返回权限字符串
? extends泛型通配符：GrantedAuthority 或其任意子类

方法实现逐行拆解

return permissions.stream()                 // 1. List<String> 转流
        .map(SimpleGrantedAuthority::new)   // 2. 每个字符串包成 SimpleGrantedAuthority
        .toList();                          // 3. 收集回 List

泛型「?」是什么

「?」是 Java 泛型的通配符。? extends GrantedAuthority = 「GrantedAuthority 或其任意子类」。作用：让返回类型更灵活通用，不写死具体是哪种权限实现。

写法含义
? extends XX 及其子类
? super XX 及其父类
?任意类型

泛型的本质作用（通俗理解）

泛型 = 给容器「贴标签」，让编译器帮我们检查类型对不对，让类型错误提前到编译期暴露，取值时不用强转。

// 没泛型：什么都塞，取值要强转，转错运行才崩
List list = new ArrayList();  list.add("字符串");  list.add(123);
String s = (String) list.get(0);  // 危险

// 有泛型：类型错误编译就报错，取值不用转
List<String> list = new ArrayList<>();
list.add(123);  // ❌ 编译报错
不必纠结 ? extends GrantedAuthority 这种泛型写法，90% 的开发平时也不深究，照框架要求写、能用就行。记住「返回一堆权限」即可。

UserDetails 接口的 7 个方法（必须全部实现）

接口方法你的实现返回值
getAuthorities()有权限列表（目前空）
getPassword()有user.getPassword()
getUsername()有user.getUsername()
isAccountNonExpired()有true（占位）
isAccountNonLocked()有true（占位）
isCredentialsNonExpired()有true（占位）
isEnabled()有user.getStatus() == 1

少实现一个，IDEA 直接报错：must be declared abstract or implement abstract method。

8. 细粒度权限（按钮级 RBAC）详解

两套权限控制

权限方式靠什么判断现状
粗粒度（按角色）roleId✅ 在用 checkAdmin / checkOwner
细粒度（按权限点）permissions 列表❌ 没接数据 传空 list

权限标识 sys:user:add 是什么

是一个「权限字符串」，按「模块:子模块:操作」命名。它不是 Spring Security 规定的关键字，而是你自己定义的标识。

sys : user : add
 │     │      └── 操作：add（新增）
 │     └───────── 子模块：user（用户）
 └─────────────── 模块：sys（系统）
权限标识含义
sys:user:add用户模块 - 新增
sys:user:delete用户模块 - 删除
sys:order:audit订单模块 - 审核

它本质就是一个普通字符串，带冒号只是为了可读、不重名。

权限标识必须「四处一致」

位置内容
数据库 sys_menu.permssys:user:add
查出来塞进 permissions["sys:user:add", ...]
getAuthorities() 返回SimpleGrantedAuthority("sys:user:add")
注解hasAuthority('sys:user:add')

「对上」是什么意思

hasAuthority('sys:user:add') 本质是一个「问句 + 判断」：当前用户权限列表里有没有 sys:user:add？

boolean has = userPermissions.stream()
    .anyMatch(a -> a.getAuthority().equals("sys:user:add"));
if (has) 放行;  else 拒绝(403);

对上 = 匹配 = 放行；没对上 = 拒绝。这就是权限控制的开关。

Collections.emptyList() 是什么

是一个「空列表」（里面啥也没有）。传它给 LoginUser 意思是「这个用户权限列表暂时为空，一个权限都不给」。后果：登录能用，但细粒度权限全部失效。这是「权限功能还没做、先用空值占位」的典型写法。

9. 如何实现细粒度权限（完整方案）

注意：光在接口上加 @PreAuthorize 注解不够，还得先准备好前置条件，否则反而所有人都会被拒。

要让注解生效，必须满足 4 个条件

条件说明现状
① 开启方法级安全注解配置类加 @EnableMethodSecurity❌ 未加
② 数据库权限数据菜单表存好权限标识需确认
③ 查权限传进 LoginUser替换 emptyList❌ 传空
④ 加注解@PreAuthorize(...)❌ 未加

完整实现（5 步）

// 第 1 步：开启注解
@Configuration
@EnableWebSecurity
@EnableMethodSecurity   // ← 加这个
public class SecurityConfig { ... }

// 第 2 步：数据库权限数据（sys_menu 加 perms 字段）
// menu_id | menu_name | perms
//   1     | 用户管理   | sys:user:add
//   2     | 用户管理   | sys:user:delete

// 第 3 步：Mapper 查权限
List<String> selectPermsByRoleId(Long roleId);

// SQL
SELECT DISTINCT m.perms FROM sys_menu m
JOIN sys_role_menu rm ON m.id = rm.menu_id
WHERE rm.role_id = #{roleId} AND m.perms IS NOT NULL AND m.perms != ''

// 第 4 步：喂给 LoginUser（两处 emptyList 都改）
List<String> perms = sysMenuMapper.selectPermsByRoleId(user.getRoleId());
return new LoginUser(user, perms);

// 第 5 步：接口加注解
@PreAuthorize("hasAuthority('sys:user:add')")
@PostMapping
public Result<Void> createUser(...) { ... }
动手前需确认 ① SecurityConfig 有没有 @EnableMethodSecurity（已确认：目前没有）；② sys_menu 表结构 + 角色菜单关联表；③ AuthService 里 selectMenuPathsByRoleId 的实现（照它风格改）。

10. 一图总结核心概念关系

┌─────────────┐        包装        ┌──────────────────┐
│   SysUser   │ ────────────────>  │    LoginUser      │
│ (数据库实体) │                    │ (implements       │
└─────────────┘                    │   UserDetails)    │
                                   └────────┬─────────┘
                                            │ getAuthorities() 返回权限
                                            ▼
                              ┌─────────────────────────┐
                              │  Collection<GrantedAuthority>  │
                              │  ["sys:user:add", ...]  │
                              └────────────┬────────────┘
                                           │ 授权判断
                                           ▼
                              @PreAuthorize("hasAuthority(...)")
                                           │
                              匹配 → 放行   不匹配 → 403

一句话记住所有概念

  • SysUser：数据库里的用户，负责存数据。
  • LoginUser：把 SysUser 包装成 Security 认的 UserDetails，是登录态的载体。
  • UserDetails：Security 要求的「契约」，LoginUser 兑现它（7 个方法）。
  • getAuthorities()：回答「用户有哪些权限」，是授权的数据源头。
  • sys:user:add：权限标识字符串，自定义，需四处一致。
  • @PreAuthorize：授权注解，靠权限字符串匹配决定放行/拒绝。
