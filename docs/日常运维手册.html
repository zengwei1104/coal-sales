容器服务名作用对外端口

二、日常启动 / 关闭 / 重启

这是最常用的操作。先进入部署目录：

cd /opt/coal-sales

▶️ 启动（开机后 / 停止后重新启动）

用已有的镜像启动所有容器，不重新编译，速度最快。

docker compose up -d

⏸️ 停止（保留容器和数据，临时关闭）

停止运行中的容器，但不删除容器和数据，随时可以再启动。

docker compose stop

▶️ 再次启动（对应上面的 stop）

docker compose start

🔄 重启（快速重启所有服务）

docker compose restart

🛑 彻底停止并删除容器（数据不丢）

删除所有容器。数据库数据存在 Docker 卷里，不会丢失，下次 up -d 会重新创建容器并复用数据。

docker compose down
记住这两个就够了：
· 平时开关 → docker compose stop / docker compose start
· 更新代码 → git pull + docker compose up -d --build

三、虚拟机关机与开机自启

3.1 关闭虚拟机会怎样

操作容器状态数据
虚拟机关机（Shut Down） 随系统停止，全部停止 ✅ 不丢。数据在 mysql-data 卷里，落盘保存
虚拟机挂起（Suspend） 进程被冻结，恢复后继续运行 ✅ 不丢，且恢复后无需任何操作
重启虚拟机（Reboot） 先停止，启动后按重启策略自动拉起 ✅ 不丢

⚠️ 容器是宿主机上的进程，系统一停容器必然停，这是正常现象，不是故障。 关键在于「重启后能不能自动起来」。

3.2 开机能否自动启动？看两个条件

要真正做到"开机即用"，需要两个条件同时满足：

#条件检查命令期望输出
1 Docker 服务设为开机自启 systemctl is-enabled docker enabled
2 容器有重启策略 docker inspect coal-web --format '{{.HostConfig.RestartPolicy.Name}}' unless-stopped

如果第 1 项是 disabled，补一条命令即可：

sudo systemctl enable docker

第 2 项由 docker-compose.yml 里的 restart: unless-stopped 保证，本项目三个服务都已配置，无需改动。

3.3 开机自启的完整流程

① 虚拟机开机
↓
② systemd 拉起 docker.service（因为 enabled）
↓
③ Docker 按 restart: unless-stopped 自动启动三个容器
↓
④ mysql 先启动并通过 healthcheck → backend 启动 → web 启动
↓
⑤ 系统可用，无需手动敲任何命令

3.4 restart 策略：unless-stopped 的含义

策略值含义手动 stop 后重启系统
no 永不自动重启 不会启动
always 总是自动重启 会启动（强制）
unless-stopped 除非被手动停止，否则自动重启 不会启动（尊重你的手动停止）
关键例外：如果你关机前手动执行过 docker compose stop， 那么重启虚拟机后容器不会自动启动（这就是 unless-stopped 的语义）。 此时需要手动执行：
cd /opt/coal-sales && docker compose start

💡 实践建议：如果你希望系统长期在线，关机时不要先 docker compose stop，直接关虚拟机即可。这样下次开机容器会自动恢复。 只有真正想临时停服时，才用 docker compose stop。

四、更新代码与版本回滚

核心原则：回滚 = 代码回退 + 重新构建 + 验证 三步。 镜像里存的是编译好的 jar 包和前端静态文件，光回滚源码不重新构建， 跑的还是旧镜像。任何代码变动（更新或回滚），都必须加 --build。

4.1 更新到最新版本（最常用）

本地改完代码并 push 到远程仓库后，在虚拟机里这样更新：

cd /opt/coal-sales
git pull                      # 拉取最新代码
docker compose up -d --build  # 必须加 --build，重新编译
docker compose ps             # 验证三个容器都 Up

--build 会重新执行 Dockerfile 编译代码，改了代码就必须加这个参数，否则会用旧镜像。

4.2 先分清：临时回滚 vs 永久回滚

类型做法适用场景特点
临时回滚
（应急止血）		 服务器上直接切到旧 commit 线上出问题，先恢复服务 快，但下次 git pull 会回到新版
永久回滚
（正式撤销）		 本地 git revert 后 push 确认那个版本就是错的 历史完整，远程分支同步

线上出事时，先用临时回滚止血，再慢慢做永久回滚。

4.3 临时回滚（线上出问题应急用）

第 1 步：找到要回到哪个版本

cd /opt/coal-sales
git log --oneline -10

输出形如：

747ddde 运维手册补充：日志查看技巧
d7bd802 排查记录补充：中文乱码
b083689 修复中文乱码：SET NAMES utf8mb4   ← 假设这个版本是好的

第 2 步：切到那个版本

git checkout b083689

会提示 You are in 'detached HEAD' state，这是正常提示，不用管。

第 3 步：重新构建并启动

docker compose up -d --build
docker compose ps

第 4 步：验证服务已恢复

docker compose logs --tail 50 backend | grep -E "Started|ERROR"

看到 Started CoalSalesApplication 就说明恢复了。

注意：临时回滚不是永久的。 之后执行 git pull 会因 HEAD 不在分支上而报错。 要回到最新版需先执行： 
git checkout main
git pull
docker compose up -d --build

4.4 永久回滚（正式撤销某个版本）

不要在服务器上 git reset --hard 后 push -f — 这会改写远程历史，以后难以追溯。用 revert，它生成反向提交，历史完整保留。

在本地（Windows）执行

cd "C:/Users/zengwei/Desktop/Spring Boot Web 煤炭销售管理系统"

# 1. 查看提交，找到有问题的那个
git log --oneline -5

# 2. 撤销指定提交（生成一个新的反向提交）
git revert <有问题的commit-hash>

# 撤多个连续提交（比如最近 2 个）
git revert --no-commit HEAD~2..HEAD
git commit -m "回滚：撤销xxx版本"

# 3. 推送
git push origin main

在服务器重新部署

cd /opt/coal-sales
git pull
docker compose up -d --build
docker compose ps

如果 revert 遇到冲突（后面的提交改过同一行）：手动编辑冲突文件，删掉 <<<<<<< / ======= / >>>>>>> 标记，然后：

git add <冲突文件>
git revert --continue

4.5 最大的坑：数据库回滚不了

这是新手最容易栽的地方。git 只管代码，数据库结构变化它一概不管。

情况回滚后会不会出问题
新版本新增了字段，你回滚到旧代码 ✅ 旧代码不认识新字段，通常不报错
新版本删除/改名了字段，你回滚到旧代码 ❌ 旧代码查这个字段 → Unknown column → 后端启动失败

回滚前先确认这次改动动没动数据库：

git diff <好版本> <坏版本> --stat -- sql/

没输出 → 只动了代码，放心回滚；有输出 → 需要手动处理数据库。

数据库回滚只有两条路：

方式做法前提
从备份恢复mysqldump 导回上线前做过备份
手动反向 SQL自己写 ALTER TABLE 撤销记得改了什么
所以：大版本上线前先备份数据库。 
docker compose exec -T mysql mysqldump -uroot -p123456 \
  --default-character-set=utf8mb4 coal_sales \
  > backup_$(date +%Y%m%d_%H%M).sql

备份文件会落在 /opt/coal-sales/ 目录下。恢复时：

docker compose exec -T mysql mysql -uroot -p123456 \
  --default-character-set=utf8mb4 coal_sales < backup_20261110_2000.sql

4.6 用 git tag 标记版本（推荐先做这个）

为什么要打 tag：commit hash 长得像 b083689，谁也记不住哪个是稳定版。 打 tag 就是给某个提交起个名字——以后回滚直接 git checkout v1.0.0，比翻 hash 清楚一个数量级。

① 打 tag（在本地执行）

# 方式一：轻量 tag（只是个名字，不推荐）
git tag v1.0.0

# 方式二：附注 tag（带作者、时间、说明，推荐）
git tag -a v1.0.0 -m "第一个正式版本：销售/库存/财务/报表全部完成"

# 给历史某个提交补打 tag（不用切过去）
git tag -a v1.0.0 b083689 -m "补打：第0.9版"

② 查看 tag

git tag                      # 列出所有 tag
git tag -l "v1.*"            # 只看 v1 开头的
git show v1.0.0              # 看某个 tag 的详情（附注 tag 才有的信息）
git describe --tags          # 看当前在哪个 tag 附近

③ 推送 tag 到远程（必做，否则虚拟机拿不到）

git push origin v1.0.0       # 推单个 tag
git push --tags              # 推所有未推送的 tag

tag 不会随普通 git push 一起上去，必须单独推。

④ 回滚到某个 tag（服务器上执行）

cd /opt/coal-sales
git fetch --tags              # 确认能拿到最新 tag 列表
git tag                       # 看有哪些版本可选
git checkout v1.0.0           # 切到该版本
docker compose up -d --build  # 必须重新构建
docker compose ps

回滚完记得回到主线：

git checkout main
git pull
docker compose up -d --build

⑤ 删除 tag（打错了 / 想收回）

git tag -d v1.0.0                    # 删本地
git push origin --delete v1.0.0      # 删远程
git push origin :refs/tags/v1.0.0    # 老版本 git 的写法

⑥ 版本号怎么定（语义化版本）

版本号什么时候升举例
v1.0.1只修 bug，不改功能修了乱码、修了某个查询报错
v1.1.0新增功能，向下兼容加了导出 Excel 功能
v2.0.0不兼容的大改动重构表结构、改了接口约定

格式：主版本.次版本.修订号。个人项目不必严格，但别用同一版本号覆盖两次。

推荐的上线流程： 
# 本地
git add . && git commit -m "完成xxx功能"
git tag -a v1.1.0 -m "新增导出功能"
git push && git push --tags

# 服务器
cd /opt/coal-sales
git pull
git fetch --tags
docker compose up -d --build
docker compose ps

先打 tag 再改代码，这样每个能跑起来的版本都有名字可回退。

4.7 进阶：给镜像打版本 tag（回滚秒级完成）

现在镜像是 coal-sales-backend:latest，每次 --build 原地覆盖，旧版本就没了。 改成打版本 tag 后，回滚只需改一行配置：

# docker-compose.yml
services:
  backend:
    image: coal-sales-backend:v1.2
  web:
    image: coal-sales-web:v1.2
# 部署某版本
docker compose build
docker tag coal-sales-backend coal-sales-backend:v1.2
docker compose up -d

# 回滚：把 compose 里的 v1.2 改成 v1.1，然后
docker compose up -d          # 几秒钟，不用重新编译
优点缺点
回滚秒级完成、不依赖网络和编译、不受源码状态影响 要养成手动打 tag 的习惯、镜像占磁盘空间

个人项目用「git + 重新构建」已足够，项目正式上线后再考虑这个方案。

五、安全发布流程（更新 + 可回退）

核心原则：回退点必须在更新之前建好，不是出了问题再去历史里翻。

5.1 常见的错误做法

做法后果
先 git pull 更新 → 发现 bug → 回头找哪个版本是好的 历史里十几个 commit，认不出哪个稳定，只能瞎试
更新前先给当前版本打 tag，再部署 ✅ 出问题 checkout v1.0.0 一条命令退回去

5.2 完整六步流程

第 0 步：更新前，把当前版本钉住（最关键）

cd /opt/coal-sales
git status                    # 确认工作区干净
git log --oneline -3          # 看当前在哪个提交
git tag                       # 看已有哪些 tag

当前版本还没有 tag 的话，现在补一个：

git tag -a v1.0.0 -m "更新前确认稳定的版本"
git push origin v1.0.0        # tag 必须单独推

git status 若有改动，说明服务器上被手动改过文件，先搞清楚再继续（正常 clone 的部署目录应当是干净的）。

第 1 步：涉及 SQL 改动时，先备份数据库

docker compose exec -T mysql mysqldump -uroot -p123456 \
  --default-character-set=utf8mb4 coal_sales \
  > backup_before_v1.1.0.sql
ls -lh backup_before_v1.1.0.sql   # 确认文件有内容

怎么判断涉不涉及 SQL：

git diff v1.0.0 origin/main --stat -- sql/

有输出 → 动了库，必须备份；无输出 → 只改代码，可跳过备份。

第 2 步：部署新版本

git pull
docker compose up -d --build

第 3 步：验证（不要跳过）

docker compose ps                                          # 三个容器都 Up
docker compose logs --tail 50 backend | grep -E "Started|ERROR"

然后打开浏览器点几个关键页面：登录、客户列表、销售单、报表。

第 4 步：发现问题 → 回退

git fetch --tags              # 确保本地有 v1.0.0
git checkout v1.0.0
docker compose up -d --build  # 必须重建，镜像里是编译产物
docker compose ps
docker compose logs --tail 30 backend | grep "Started"

如果数据库也被新版本改坏了，再恢复备份：

docker compose exec -T mysql mysql -uroot -p123456 \
  --default-character-set=utf8mb4 coal_sales < backup_before_v1.1.0.sql

第 5 步：确认稳定后，给新版本也打 tag

git checkout main             # 先脱离 tag 状态回到主线
git pull
git tag -a v1.1.0 -m "新增xxx功能"
git push origin v1.1.0

5.3 时间线示意

时刻服务器状态你能回到哪
更新前main @ 旧提交，已打 v1.0.0随时 checkout v1.0.0
更新后正常main @ 新提交v1.0.0 仍可退
更新后出 bug任意状态checkout v1.0.0 + --build，2~3 分钟恢复
确认稳定新版本打上 v1.1.0两个回退点都在

5.4 三个必踩的坑

坑说明怎么避
坑 1
本地改动没提交就发布		 服务器 git pull 只拿远程代码，本地未 commit 的改动不会过去 发布前先 git status，有改动就 add + commit + push
坑 2
tag 不会自动同步		 git push 不推 tag 本地 git push origin v1.0.0，服务器 git fetch --tags
坑 3
回退忘了 --build		 镜像里是上一次编译好的 jar 和静态文件，只切源码不重建 = 没退 任何代码变动（更新或回退）都加 --build

5.5 一行速记

打 tag → 备份库 → git pull → up -d --build → 验证
                                      ↓ 出问题
                        git checkout v1.0.0 → up -d --build

5.6 想让回退更快（可选）

回退时 --build 有缓存，一般 1~3 分钟。想秒级回退，可在更新前把当前镜像存一份：

# 更新前执行
docker tag coal-sales-backend coal-sales-backend:v1.0.0
docker tag coal-sales-web coal-sales-web:v1.0.0

回退时把 docker-compose.yml 里两个服务的 image: 指向 :v1.0.0，然后：

docker compose up -d          # 不带 --build，几秒钟完成

当前项目用的是 build: 方式，属于进阶优化，需要时再改配置。

六、查看状态与日志

📋 查看容器状态

三个容器都应显示 running（或 Up）。

docker compose ps

6.1 两种看日志的方式

方式命令特点适用场景
一次性输出 ✅ 推荐 docker compose logs --tail 50 backend 输出固定一段，看完自动回到命令行 日常排查问题
实时滚动 docker compose logs -f backend 持续输出新日志，需手动退出 观察启动过程、复现问题时
为什么优先用 --tail 而不是 -f： 排查问题时，-f 会一直往下刷，历史报错被瞬间冲走，很难看清； --tail 50 是一次性输出完整一段日志，更容易定位异常。

6.2 常用日志命令

📄 看最后 N 行（最常用）

docker compose logs --tail 50 backend   # 后端最后 50 行
docker compose logs --tail 100 web      # 前端最后 100 行
docker compose logs --tail 50 mysql     # 数据库最后 50 行

🕐 按时间范围看

docker compose logs --since 10m     # 最近 10 分钟
docker compose logs --since 2h      # 最近 2 小时
docker compose logs --since 1d      # 最近 1 天

🔍 只看报错（过滤关键字）

docker compose logs --tail 200 backend | grep -i error
docker compose logs --tail 200 backend | grep -iE "error|exception|failed"

日志太长时先过滤，能快速定位问题行。

📚 看全部日志 / 全部服务

docker compose logs              # 所有服务的日志
docker compose logs backend      # 只看后端
docker compose logs mysql        # 只看数据库
docker compose logs web          # 只看前端

6.3 怎么退出日志查看

当前状态退出方式容器会怎样
正在 logs -f 实时滚动 按 Ctrl + C ✅ 继续运行，只是停止查看
输出过长，进入了分页模式（less） 按 q ✅ 不影响
用 docker compose up（没加 -d）启动的 按 Ctrl + C ⚠️ 会停止容器
放心按 Ctrl+C： 正常部署用的都是 docker compose up -d（后台运行）， 此时看日志按 Ctrl+C 只是退出查看，容器不受任何影响。

6.4 判断后端是否启动成功

看后端日志，出现下面两行才算真的起来了：

Tomcat started on port 8080
Started CoalSalesApplication in x.xxx seconds

如果看到这些关键字，说明有问题：

日志关键字含义
Communications link failure连不上 MySQL，检查 mysql 容器是否 healthy
Access denied for user数据库账号密码错误
Unknown database数据库没初始化，需要 down -v 重来
Application run failed启动过程报错，往上翻找第一个 Exception

7.1 五个容易混淆的命令对比

命令是否重新编译容器数据典型场景
up -d 否 存在则启动，缺失则创建 保留 日常开机启动
up -d --build 是 重新构建镜像后启动 保留 改了代码 / 改了 Dockerfile
start 否 只启动已停止的容器 保留 配合 stop 使用
restart 否 重启运行中的容器 保留 服务卡住想快速恢复
down — 删除容器和网络 保留（卷还在） 彻底清理后重建
down -v — 删除容器和网络 全删 需要重新初始化数据库

八、常见问题

问题排查 / 解决
提示「找不到 docker-compose.yml」没进对目录，先 cd /opt/coal-sales
页面打不开先 docker compose ps 看三个容器是否都 running；再 docker compose logs -f backend 看后端是否报错
改了代码但没生效是不是忘了加 --build？更新必须用 docker compose up -d --build
重启后数据还在吗在。数据库数据存在 mysql-data 卷里，stop / restart / down 都不会丢
想彻底清空数据库重来删除卷：docker compose down -v（⚠️ 会删除所有数据，慎用）
关闭虚拟机后项目会自己停吗 会。容器是宿主机进程，系统停止容器必然停止，但数据不丢（存在数据卷里）
重启虚拟机后要手动启动吗 正常不需要。只要 systemctl is-enabled docker 输出 enabled，且容器策略为 unless-stopped，开机会自动拉起。 但如果关机前手动执行过 docker compose stop，则需手动 docker compose start
怎么确认开机自启已生效 systemctl is-enabled docker → 应为 enabled； docker inspect coal-web --format '{{.HostConfig.RestartPolicy.Name}}' → 应为 unless-stopped
开机自启没生效怎么修 sudo systemctl enable docker，然后重启虚拟机验证
数据库中文变成乱码 初始化导入时客户端字符集为 latin1 导致。需确保 SQL 脚本首行有 SET NAMES utf8mb4;，然后 docker compose down -v && docker compose up -d 重新初始化。 详见《部署问题排查记录》
日志刷太快看不清 别用 -f，改用 docker compose logs --tail 100 backend； 或直接过滤：docker compose logs --tail 200 backend | grep -i error
看日志按 Ctrl+C 容器会不会停 不会。只退出日志查看，容器继续运行。 只有用 docker compose up（不带 -d）启动时， Ctrl+C 才会停止容器
日志滚动卡住 / 无法回到命令行 先按 Ctrl+C；若进入了分页模式（less）按 q； 实在不行直接关闭终端窗口，不影响容器
怎么看某个时间段发生了什么 docker compose logs --since 10m backend（最近 10 分钟）， 也支持 2h、1d
新版本有问题，怎么快速回到上一个版本 git log --oneline -10 找到好版本的 hash → git checkout <hash> → docker compose up -d --build。 这是临时回滚，详见 4.3
怎么安全地更新版本，出问题又能退回来 更新前先打 tag 钉住当前稳定版，再备份库、部署、验证。 完整六步流程见 5.2
回滚后 git pull 报错 "not currently on a branch" 因为处于 detached HEAD 状态。执行 git checkout main → git pull → up -d --build 即可回到最新版
怎么彻底撤销某个错误版本 本地 git revert <hash> 生成反向提交 → push → 服务器 git pull + up -d --build。 不要用 reset --hard + push -f，详见 4.4
回滚代码后后端启动报 Unknown column 数据库结构没跟着回滚。数据库不受 git 管理， 需从备份恢复或手动执行反向 SQL，详见 4.5
回滚后页面还是新的 / 没生效 忘了加 --build。镜像里是旧的编译产物， 改任何代码（更新或回滚）都必须重新构建
怎么备份数据库 docker compose exec -T mysql mysqldump -uroot -p123456 --default-character-set=utf8mb4 coal_sales > backup_日期.sql， 建议大版本上线前执行
怎么给版本起名字，方便以后回滚 git tag -a v1.0.0 -m "版本说明" → git push origin v1.0.0。 以后直接 git checkout v1.0.0 回滚，详见 4.6
tag 打了，但虚拟机里 git tag 看不到 忘了推 tag（tag 不会随 git push 自动上去）。 本地执行 git push --tags，服务器执行 git fetch --tags
tag 打完发现打错了，怎么撤销 git tag -d v1.0.0 删本地 → git push origin --delete v1.0.0 删远程
