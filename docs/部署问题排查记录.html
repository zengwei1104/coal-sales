问题 1 · 拉取 MySQL 镜像失败

现象

✘ Image mysql:8.0 Error failed to resolve reference "docker.io/library/mysql:8.0"
Error response from daemon: failed to resolve reference "docker.io/library/mysql:8.0":
failed to do request: Head "https://registry-1.docker.io/v2/library/mysql/manifests/8.0":
dial tcp 103.56.16.112:443: connect: connection refused
根因 Docker 默认从 Docker Hub（docker.io）拉取镜像，而国内网络访问该域名会被阻断， 直接报 connection refused（连接被拒绝，不是"慢"）。
解决 配置国内镜像加速器，写入 /etc/docker/daemon.json，重启 Docker 生效。

操作步骤：

sudo mkdir -p /etc/docker

sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://dockerproxy.com",
    "https://docker.nju.edu.cn"
  ]
}
EOF

sudo systemctl daemon-reload
sudo systemctl restart docker

验证：能看到三个镜像源即生效。

docker info | grep -A5 "Registry Mirrors"

问题 2 · 前端 npm install 超时

现象

[web build 4/6] RUN npm install
npm error code ETIMEDOUT
npm error network request to https://registry.npmmirror.com/tinyglobby/-/tinyglobby-0.2.17.tgz
       failed, reason:
npm error network This is a problem related to network connectivity.
根因 coal-web/package-lock.json 里 121 个依赖包的 resolved 下载地址 被锁死成了 registry.npmmirror.com（本地开发机的 npm 全局源是淘宝镜像）。 容器内执行 npm install 会严格按 lock 里的地址下载，而该源在虚拟机网络下请求超时。

同时 node:20 版本偏低，vite@8、@vueuse/core@15 都要求 node >= 22，触发 EBADENGINE 警告。
解决 ① Dockerfile 内强制使用官方 npm 源；② Node 升级到 22。 
FROM node:22-alpine AS build
WORKDIR /app

# 强制使用官方 npm 源
RUN npm config set registry https://registry.npmjs.org/

COPY package*.json ./
RUN npm install
注意：仅设置 npm config set registry 还不够——若 lock 文件里已有绝对 resolved 地址，npm 仍会按 lock 下载。必须同时清理/重新生成 lock 文件。

问题 3 · vite build 找不到原生绑定（最关键）

现象

=> ERROR [web build 7/7] RUN npm run build
> vite build

Error: Cannot find native binding. npm has a bug related to optional dependencies.
    cause: Error: Cannot find module '@rolldown/binding-wasm32-wasi'
    cause: Error: Cannot find module '@rolldown/binding-linux-x64-musl'
    cause: Error: Cannot find module './rolldown-binding.linux-x64-musl.node'
根因 vite@8 使用 rolldown（Rust 编写的打包器），需要对应平台的 原生二进制模块。这些平台绑定通过 npm 的 optional dependencies 分发 （每个平台一个包，安装时只装当前平台的那个）。

package-lock.json 是在 Windows 上生成的，只记录了 Windows 平台的绑定条目，Linux/musl 的条目根本没被写进 lock。 容器（Linux + Alpine）内按 lock 安装，自然缺少 @rolldown/binding-linux-x64-musl，构建时加载失败。

这是本次部署最隐蔽的坑：本地能跑，容器里必炸。
解决 容器内不使用 Windows 生成的 lock 文件，让 npm 在 Linux 环境中现场解析依赖。

方案 A（采用）：只复制 package.json，不复制 lock

# coal-web/Dockerfile
COPY package.json ./
RUN npm install

方案 B：跨平台安装（保留 lock 时可用）

RUN npm install --os=linux --cpu=x64 --libc=musl

配套：新增 coal-web/.dockerignore，防止本地 node_modules 污染镜像

node_modules
dist
dist-ssr
package-lock.json
代价：放弃版本锁定（每次构建按 semver 取最新兼容版本）。对个人项目可接受， 换来的是构建稳定。若要严格锁版本，建议在 Linux 环境下生成 lock 文件。

问题 4 · 多行命令粘贴后终端卡住

现象

[zengwei@localhost coal-sales]$ sudo tee /etc/docker/daemon.json > /dev/null <<'EOF' { ... } EOF sudo systemctl ...
> 
>
卡住了
根因 多条命令被粘贴成一行，heredoc 的结束符 EOF 没有单独成行， Shell 认为输入还没结束，持续显示 > 等待后续输入。
解决 按 Ctrl+C 退出，然后一条一条执行，确保 EOF 单独一行且顶格（前面不能有空格）。

问题 5 · git push 无法输入账号密码

现象

$ git push origin main
fatal: could not read Username for 'https://github.com': terminal prompts disabled
根因 非交互式终端无法弹出凭证输入提示，HTTPS 方式推送 GitHub 需要用户名 + Personal Access Token。
解决 在自己的终端里手动执行一次 git push 并输入凭证，之后凭证会被缓存， 后续自动推送即可成功。

凭证说明：密码不是 GitHub 登录密码，而是 Personal Access Token（GitHub → Settings → Developer settings → Personal access tokens）。

问题 6 · 关键部署文件没进 git 仓库

现象

git ls-files 检查发现，以下关键文件完全没有被 git 跟踪：

  • coal-web/package.json / package-lock.json（前端构建必需）
  • coal-web/Dockerfile / nginx.conf
  • coal-sales/Dockerfile
  • docker-compose.yml

如果直接 git clone 到服务器，前端会因缺少 package.json 而构建失败。

根因 根目录 .gitignore 末尾有三条不带路径前缀的规则： 
node_modules/
package-lock.json
package.json
这类规则会匹配所有层级的同名文件，把 coal-web/package.json 也一起忽略了。
解决 加上 / 前缀，限定只忽略根目录下的同名文件。 
# 根目录下的前端依赖（可能是误操作生成的）
/node_modules/
/package-lock.json
/package.json

问题 7 · 部署文件换行符被转成 CRLF

现象

warning: in the working copy of 'coal-web/Dockerfile', LF will be replaced by CRLF
warning: in the working copy of 'docker-compose.yml', LF will be replaced by CRLF
根因 Windows 上 Git 默认 core.autocrlf=true，检出时会把 LF 转成 CRLF。 而 Dockerfile、shell 脚本、nginx.conf 等在 Linux 容器内执行时更适应 LF， CRLF 可能导致脚本执行异常（如 /bin/sh^M: bad interpreter）。
解决 新增根目录 .gitattributes，强制关键文件使用 LF。 
# 强制部署关键文件使用 LF 换行符
*.sh text eol=lf
Dockerfile text eol=lf
*.conf text eol=lf
docker-compose.yml text eol=lf
*.sql text eol=lf
mvnw text eol=lf

但英文、数字显示正常（如 admin、13800000001）。

排查过程（逐步定位在哪一层坏掉）

排查项检查方法结论
SQL 脚本文件本身编码 用 Python 逐个 decode('utf-8') ✅ 全部 UTF-8，文件没问题
数据表字符集 SHOW CREATE TABLE sys_user; ✅ 均为 DEFAULT CHARSET=utf8mb4
MySQL 服务端字符集 SHOW VARIABLES LIKE 'character_set_server'; ✅ utf8mb4（compose 已配置）
数据库里存的数据 见下方查询命令 ❌ 查出来就是乱码 → 数据在入库时就坏了

关键判定命令：

docker compose exec mysql mysql -uroot -p123456 \
  --default-character-set=utf8mb4 coal_sales \
  -e "SELECT username, real_name FROM sys_user LIMIT 3;"
输出判断
admin │ 系统管理员数据库是好的，问题在前端/后端显示层
admin │ ç³»ç»Ÿç®¡ç†å‘˜ 数据库里的数据已损坏，需重新导入
根因 MySQL 官方镜像在首次启动时，会由 docker-entrypoint.sh 自动执行 /docker-entrypoint-initdb.d/ 下的 SQL 脚本。它调用的是 mysql 命令行客户端，而该客户端的 --default-character-set 默认值取自操作系统 locale。 容器内通常没有设置 LANG 环境变量，locale 为 POSIX/C， 于是客户端字符集回退为 latin1。

结果：SQL 文件里 UTF-8 编码的中文字节 × 被当作 latin1 解读 × 再转存为 utf8mb4 = 双重编码乱码（mojibake）。这类乱码是不可逆的， 无法通过改配置修复，只能重新导入。

陷阱：初始化脚本只在数据目录为空时执行一次。 即使后来把 SQL 文件改对了，只要数据卷还在，就不会重新导入——必须清空数据卷。
解决 ① 从 SQL 脚本层面根治（永久生效）；② 清空数据卷重新初始化。

方案 A（推荐，永久生效）：每个 SQL 脚本头部加 SET NAMES

在 sql/ 下每个 .sql 文件的第一行加上：

SET NAMES utf8mb4;

这条语句会把当前会话的 character_set_client、 character_set_connection、character_set_results 全部设为 utf8mb4，不再依赖客户端默认值。 这样无论以后谁在什么环境下重新部署，导入都不会乱码。

方案 B：清空数据卷，让 MySQL 重新初始化

cd /opt/coal-sales
git pull                     # 拉取修复后的 SQL 脚本

docker compose down -v       # ⚠️ -v 会删除数据卷（含数据库数据）
docker compose up -d         # 重新初始化，自动执行带 SET NAMES 的脚本
注意：-v 会删除数据库数据。仅在"数据全是初始化种子数据、 可以丢弃"的情况下使用。若已有真实业务数据，请改用 mysqldump 备份后再恢复。

方案 C：不清卷，手动重新导入

docker compose stop backend

# 删库重建（显式指定 utf8mb4）
docker compose exec -T mysql mysql -uroot -p123456 -e \
"DROP DATABASE IF EXISTS coal_sales; CREATE DATABASE coal_sales CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;"

# 逐个导入，-T 不能少（否则 stdin 重定向不生效）
for f in sql/0*.sql; do
  echo "=== 导入 $f ==="
  docker compose exec -T mysql mysql -uroot -p123456 \
    --default-character-set=utf8mb4 coal_sales < "$f"
done

docker compose start backend

验证

docker compose exec mysql mysql -uroot -p123456 \
  --default-character-set=utf8mb4 coal_sales \
  -e "SELECT username, real_name FROM sys_user LIMIT 3;"

期望输出：

+----------+----------------+
| username | real_name      |
+----------+----------------+
| admin    | 系统管理员     |
| manager  | 销售经理       |
| sales    | 销售员         |
+----------+----------------+

然后浏览器 Ctrl+F5 强制刷新页面。

如何区分乱码类型：
· ç³»ç»Ÿç®¡ç†å‘˜ 这类带重音符号的 → UTF-8 被按 latin1 解读（本文场景）；
· 系统管理员 显示为 ?????? → 目标字符集不支持该字符；
· 显示为 \u7cfb\u7edf → 是 JSON 序列化层的问题，不是数据库。

问题 9 · git 弹窗要求选择凭证助手

现象

在 Windows 上执行 git push 时，弹出标题为 CredentialHelper 的对话框：

Select a credential helper
  ◯ <no helper>
  ◉ manager
  ◯ wincred
☐ Always use this from now on
                            [ Select ]  [ Cancel ]

或者在非交互终端里直接报错：

fatal: could not read Username for 'https://github.com': terminal prompts disabled
根因 Windows 版 Git 没有配置凭证助手（credential helper）。 使用 HTTPS 方式推送 GitHub 必须提供用户名 + Personal Access Token， Git 不知道该用什么方式保存/读取这份凭证，于是弹出选择框； 在无法交互的终端中，则直接报 terminal prompts disabled 失败。
解决 选择 manager（Git Credential Manager），并勾选 Always use this from now on，点 Select。 随后按提示在浏览器登录 GitHub 授权一次，凭证即被加密保存到 Windows 凭据管理器。

三个选项对比

选项含义推荐度
<no helper> 不保存任何凭证，每次 push 都要重新输入账号密码 ❌ 不推荐
manager Git Credential Manager（GCM），现代方案。支持浏览器一键 OAuth 登录 GitHub， 凭证加密存储在 Windows 凭据管理器，支持双因素认证 ✅ 推荐
wincred 旧版 Windows 凭据管理器，只保存用户名密码，不支持 OAuth/2FA ⚠️ 能用但过时

也可以用命令直接配置（等价操作）

git config --global credential.helper manager

验证

git config --global --get credential.helper
# 输出 manager 即配置成功

git push
# 不再要求输入账号密码即可推送
凭证说明：GitHub 已不支持用登录密码做 HTTPS 认证， 必须使用 Personal Access Token （GitHub → Settings → Developer settings → Personal access tokens）。 使用 manager 时通常无需手动生成，浏览器授权即可。

二、根因总结

9 个问题看似零散，实际上可以归为四大类：

类别涉及问题本质
跨平台差异
Windows 开发 → Linux 部署		 问题 3、问题 7、问题 9 依赖里的原生模块（rolldown / esbuild / sharp 等）各平台编译不同版本； 换行符约定、凭证管理机制也不同。本地能跑 ≠ 容器能跑。
国内网络环境 问题 1、问题 2 Docker Hub、npm 官方源、Maven 中央仓库在国内访问不稳定， 必须配置国内镜像加速（Docker 镜像源 / npm 源 / 阿里云 Maven 镜像）。
字符集与编码 问题 8 容器内缺少 LANG 导致 MySQL 客户端默认 latin1， UTF-8 中文按 latin1 解读后不可逆损坏。 必须在 SQL 脚本内显式 SET NAMES utf8mb4， 不能依赖客户端默认值。
工程配置疏漏 问题 4、5、6 .gitignore 规则写得太宽泛、未配置凭证助手、多行命令粘贴方式不当。
核心认知：首次 Docker 构建需要下载约 2GB 基础镜像 + npm 全套依赖 + Maven 全套依赖， 任一环节网络、平台或编码不匹配就会失败。这类问题属于一次性成本—— 镜像构建成功后即固化，后续 docker compose up -d 只需几秒，无需联网。

特别提醒：问题 8（乱码）和问题 3（原生绑定）这类"数据/产物一旦生成就是错的"问题， 改配置无法补救，只能重新生成——所以修复后必须重跑导入、重建镜像。

三、避坑清单（重要）

3.1 部署前必查

序号检查项命令 / 做法
1 Docker 镜像加速器已配置 docker info | grep -A5 "Registry Mirrors"
2 关键文件已被 git 跟踪 git ls-files | grep -E "Dockerfile|compose|package.json"
3 容器内不复用 Windows 生成的 lock Dockerfile 用 COPY package.json ./，或加 --os=linux
4 已配置 .dockerignore 排除 node_modules、dist、target
5 Maven 走国内镜像 阿里云 maven.aliyun.com/repository/public
6 SQL 脚本首行有 SET NAMES grep -L "SET NAMES utf8mb4" sql/*.sql，无输出即全部已加
7 Git 凭证助手已配置 git config --global --get credential.helper 应输出 manager

3.2 以后新增前端依赖时

如果新装的依赖带原生模块（sharp、canvas、rolldown、esbuild 等），可能再次出现"平台绑定缺失"。

规避方法：

  • 不要在 Windows 上生成 lock 后直接用于 Linux 容器构建；
  • 或安装时显式指定目标平台：npm install --os=linux --cpu=x64 --libc=musl；
  • 或直接在容器内执行 npm install 验证。

3.3 以后新增 SQL 脚本时

每个新加的 .sql 脚本，第一行都要写 SET NAMES utf8mb4;。 否则一旦数据卷被清空、MySQL 重新初始化，该脚本里的中文会再次变成乱码。

如果不小心已经导入坏了，只能重新导入修复：

docker compose down -v && docker compose up -d

有真实数据时改用 mysqldump 备份 → 修好脚本 → 恢复。

3.4 命令操作注意

场景注意点
粘贴多行命令 heredoc 的 EOF 必须单独一行顶格；否则按 Ctrl+C 退出后分步执行
git push 先在 Windows 上确认凭证助手为 manager （git config --global credential.helper）， 并在弹出的 CredentialHelper 对话框中选中 manager + Always use this from now on
查询数据库中文 务必带 --default-character-set=utf8mb4， 否则明明数据是对的，用 latin1 客户端查出来也会显示乱码，造成误判
首次构建 耗时可能 20 分钟以上，中途不要 Ctrl+C
改了代码后 必须用 docker compose up -d --build，否则仍用旧镜像
改了 SQL 脚本后 不会自动重新导入。需 docker compose down -v 清空数据卷后重启， 或手动 --default-character-set=utf8mb4 重新导入

3.5 正确的最终 Dockerfile

coal-web/Dockerfile（前端）

# ===== 构建阶段：Node 22 打包前端 =====
FROM node:22-alpine AS build
WORKDIR /app

# 强制使用官方 npm 源
RUN npm config set registry https://registry.npmjs.org/

# 只复制 package.json，不带 lock 文件
# 原因：package-lock.json 在 Windows 上生成，只记录了 Windows 平台的 rolldown 原生绑定，
# 容器内（Linux/musl）按 lock 安装会缺 @rolldown/binding-linux-x64-musl，
# 导致 vite build 报 "Cannot find native binding"。
COPY package.json ./
RUN npm install

COPY . .
RUN npm run build

# ===== 运行阶段：Nginx 托管静态文件 =====
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

coal-sales/Dockerfile（后端）

sql/01-permission.sql（所有 SQL 脚本统一格式）

-- =============================================================
