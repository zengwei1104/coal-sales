## 1 概述

概要设计基于《01-需求规格说明书 v2.3》展开，确定系统的模块划分与数据实体关系，作为数据库设计与详细编码的依据。

### 1.1 设计目标

1. 将需求中的 7 大功能模块映射为清晰的代码分层。
2. 确定系统全部实体及其关系，为数据库设计提供直接输入。
3. 用少量关键流程验证设计能否支撑业务闭环。

### 1.2 设计原则

| 原则      | 说明                        |
| ------- | ------------------------- |
| 单证同源    | 所有单据保留上游单据号，任一单据可追溯上下游    |
| 计量与业务解耦 | 磅房只做计量录入，业务判断在销售与财务       |
| 结果与过程分离 | 库存是结果（当前数），流水是过程（每次变动）    |
| 审批只设两端  | 合同（承诺）与结算（确认）设审批，执行动作日志留痕 |
| 业务规则参数化 | 阈值存数据字典，改规则不改代码           |

## 3 数据实体与关系

### 3.1 实体清单（17 张表）

| 分类   | 实体   | 英文表名            | 说明       |
| ---- | ---- | --------------- | -------- |
| 权限   | 用户   | sys_user        | 登录账号     |
| 权限   | 角色   | sys_role        | 6 个岗位    |
| 权限   | 菜单   | sys_menu        | 可访问页面    |
| 权限   | 角色菜单 | sys_role_menu   | 角色-菜单映射  |
| 基础数据 | 客户   | customer        | 买方单位     |
| 基础数据 | 煤种商品 | coal_product    | 煤种、规格、热值 |
| 基础数据 | 数据字典 | sys_dict        | 业务参数     |
| 销售   | 合同   | contract        | 约定量价     |
| 销售   | 订单   | sale_order      | 分批计划     |
| 销售   | 磅单   | weigh_ticket    | 实际计量     |
| 库存   | 库存   | stock           | 当前库存     |
| 库存   | 库存流水 | stock_record    | 每次变动     |
| 财务   | 结算单  | settlement      | 应收账单     |
| 财务   | 结算明细 | settlement_item | 结算单每一行   |
| 财务   | 回款   | payment         | 收款登记     |
| 财务   | 核销明细 | write_off       | 回款冲抵结算   |
| 审计   | 操作日志 | sys_log         | 关键动作留痕   |

> 盘点记录不单独建表，并入库存流水（来源类型=盘点），盘盈盘亏原因记在流水备注。  
> 应收账款不建表，由「已审核且未核销的结算单金额」实时计算。

### 3.2 销售主链关系

```
客户 ──1:N── 合同 ──1:N── 订单 ──1:N── 磅单
  │                │                     │
  │                └────1:N── 结算单 ──1:N── 结算明细 ──0..1:1── 磅单
  │                                    （结算明细关联磅单，最多结算一次）
  └────1:N── 回款 ──1:N── 核销明细 ──N:1── 结算单
```

关键基数：

| 关系         | 基数       | 说明             |
| ---------- | -------- | -------------- |
| 客户 → 合同    | 1 : N    | 一个客户多份合同       |
| 煤种商品 → 合同  | 1 : N    | 一合同一煤种（单煤种，C1） |
| 合同 → 订单    | 1 : N    | N=1 即一单一合同     |
| 订单 → 磅单    | 1 : N    | 一订单多车发运        |
| 合同 → 结算单   | 1 : N    | 结算单挂合同，不挂订单    |
| 结算单 → 结算明细 | 1 : N    | 一结算单含多行        |
| 磅单 → 结算明细  | 0..1 : 1 | 一磅单最多被结算一次     |
| 客户 → 回款    | 1 : N    | 一客户多次付款        |
| 回款 → 核销明细  | 1 : N    | 一笔回款冲多张结算单     |
| 结算单 → 核销明细 | 1 : N    | 一结算单可分次收款      |

### 3.3 库存侧关系

```
煤种商品 ──1:1── 库存（当前库存，每种煤一条记录）
库存 ──1:N── 库存流水（每次变动一笔，只增不改）
库存流水.来源 ← 通用指针：source_type + source_id（入库/磅单/盘点）
```

库存 = 期初 + 入库 − 出库 ± 盘点调整（账实核对依据）。

### 3.4 权限侧关系（RBAC）

```
用户 ──N:1── 角色 ──1:N── 角色菜单 ──N:1── 菜单
```

用户与菜单不直接关联，经角色中转，实现「配一次角色，多人共用」。

### 3.5 系统侧（独立实体）

| 实体            | 关联性                 |
| ------------- | ------------------- |
| 数据字典 sys_dict | 独立，不与其他表外键关联        |
| 操作日志 sys_log  | 独立，记录操作人、时间、动作，事后检索 |

## 4 关键设计决策

| # | 决策                                 | 理由                         |
| - | ---------------------------------- | -------------------------- |
| 1 | 结算单挂合同，不挂订单                        | 月结需合并多订单磅单，挂订单无法汇总对账       |
| 2 | 磅单→结算明细为 0..1                      | 一磅单只能结算一次，防重复计费，数据库层唯一约束兜底 |
| 3 | 结算明细独立建表                           | 一结算单含不定数量的磅单，需拆「总账/分账」两层   |
| 4 | 库存流水来源用通用指针（source_type+source_id） | 新增来源（退货、调拨）不改表，扩展性好        |
| 5 | 盘点、应收账款不单独建表                       | 分别用流水备注、实时计算代替，够用且少维护      |
| 6 | 权限走 RBAC 四表                        | 角色中间层，避免逐人配权限              |

## 5 鉴权设计

### 5.1 选型结论

采用 **Spring Security + JWT** 无状态鉴权方案，密码使用 BCrypt 加密。

### 5.2 鉴权流程

```
登录：POST /api/auth/login
  → 查用户 → BCrypt 校验密码 → 签发 JWT（含用户ID、角色）→ 返回 token

请求：携带 Authorization: Bearer <token>
  → 经过 SecurityFilterChain
  → JwtAuthenticationFilter 解析 token，验证签名与有效期
  → 认证成功后写入 SecurityContext
  → 授权层按角色判定菜单权限
  → 放行 或 返回 401（未认证）/ 403（越权）
```

### 5.3 组件构成

| 组件                      | 职责                                                       |
| ----------------------- | -------------------------------------------------------- |
| SecurityConfig          | 定义 SecurityFilterChain：放行登录接口、注册 JWT 过滤器、关闭 CSRF、配置无状态会话 |
| JwtAuthenticationFilter | 每次请求解析并校验 token，认证成功后放入 SecurityContextHolder            |
| UserDetailsServiceImpl  | 按用户名加载用户及其角色，供认证使用                                       |
| JwtUtil                 | token 的生成、解析、有效期校验                                       |
| PasswordEncoder         | BCrypt 加密与匹配（`spring-security-crypto` 提供）                |

### 5.4 与需求的对齐

| 需求编号                | 落实方式                          |
| ------------------- | ----------------------------- |
| N07 密码 BCrypt 存储    | PasswordEncoder 编码后入库，库中不可见明文 |
| N08 JWT 有效期 2 小时    | token 生成时设置过期时间               |
| N09 未携带/失效返回 401    | 过滤器校验失败返回 401                 |
| N10 越权返回 403        | 授权层按角色判定                      |
| N13 连续 5 次错误锁 15 分钟 | 登录 Service 计数，参数取字典表          |

### 5.5 方案对比（选型依据）

| 维度             | 自研 JWT + 拦截器 | 全套 Spring Security（采用） |
| -------------- | ------------ | ---------------------- |
| 核心代码量          | ~40 行        | 多类 + 配置                |
| 概念负担           | 低            | 高（过滤器链/认证管理器/上下文）      |
| 密码安全           | BCrypt       | BCrypt                 |
| 无状态 JWT        | 支持           | 支持                     |
| 后续扩展（OAuth2 等） | 需自写          | 天然支持                   |
| 就业/简历价值        | 一般           | 高                      |

**取舍说明**：全套 Spring Security 对答辩的要求更高——必须真正理解过滤器链与认证流程，否则被深问易卡壳。选择它看重的是「企业主流 + 简历价值」，因此编码阶段需额外投入时间吃透其原理。
